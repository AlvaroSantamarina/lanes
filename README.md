# lanes

A method for building software with Claude Code when one session is not enough: **one coordination session, several lane sessions working in parallel, and the repo as the only shared memory.**

It came out of building a real product (a CRM with a WhatsApp sales bot) end to end with ~20 briefs, three parallel lanes and one human owner. This plugin packages what worked so it can be repeated: not automated, **standardized**.

## The shape

```
            owner (decides, approves plans, merges)
                 │
        coordination session ──── writes briefs, keeps memory and roadmap true,
                 │                 reviews plans, relays, never writes product code
     ┌───────────┼───────────┐
   lane 1      lane 2      lane 3     ← one brief each: plan → OK → test-first → PR
     │           │           │
     └──────── the repo ─────┘        CLAUDE.md · decisions · memory · briefs · plans
```

**Phases**

1. **System design** — decisions numbered and written down, open questions with provisional assumptions, the work carved into a sequential **core** and parallel **waves**.
2. **Core** — a handful of briefs, one after another, until a milestone works end to end with mocks.
3. **Waves** — briefs on disjoint modules, run in parallel lanes.

**The loop for every brief**

1. The coordination writes the **brief** (the *what*, one page) and reserves its decision number.
2. A lane session reads only what the brief lists and writes the **plan** (the *how*), with tests first and questions for the owner, each with a recommendation.
3. The coordination runs an **auditor** on the plan — it verifies the plan's load-bearing claims against the code, on a budget, without re-planning — and hands the owner one paste-ready block: *"OK to the plan with these adjustments"*.
4. The lane **compacts** at the plan→code boundary (the plan carries its own "context for implementation"), implements test-first, runs the checks and the review agents, fills "What's left", and opens the PR with a fixed final report.
5. The owner merges; the lane cleans up, `/clear`, next brief.

## Principles

- **The repo is the memory.** Decisions, state, carry-overs and gotchas live in files every session reads (`docs/decisions.md`, `docs/memory.md`). Nothing important lives only in one session's context — so compactions and new sessions lose nothing.
- **Brief = what, plan = how.** The person closest to the code writes the how, with the code in view.
- **No code before the plan is approved.**
- **Verify, don't re-plan.** Reviews look for false claims, contradictions and gaps. That is where the real bugs were (a cron option that silently does nothing, a trigger the plan said didn't exist, a constraint that would break old rows), at a fraction of the cost of redoing the planning.
- **Recommend, don't just ask.** Every question to the owner comes with options and a recommended one.
- **Decouple only what is likely to change.** Swappable pieces where vendors and models change; plain direct code everywhere else.
- **Small PRs, squash merges, one brief = one branch = one PR.**

## What's in the plugin

| Piece | Use it when |
|---|---|
| `skills/system-design` | Starting a project (or a big new part): decisions, roadmap, scaffolding |
| `skills/coordination` | This session coordinates, or resumes coordinating after a compaction |
| `skills/writing-briefs` | Writing a brief or a batch, including the pre-push audit |
| `skills/reviewing-plans` | A lane says "plan written, waiting for your OK", or "PR open" |
| `agents/auditor` | Auditing a plan or a brief (Opus, fixed budget and output) |
| `templates/` | `CLAUDE.md` (session protocol, final report, definition of done), `decisions.md`, `memory.md`, `INDEX.md`, `brief.md`, `plan.md` |

The lane sessions need no skill: their protocol is in the project's `CLAUDE.md`, which every session loads automatically.

## Install

```
/plugin marketplace add AlvaroSantamarina/lanes
/plugin install lanes@lanes
```

Then, in the session that will coordinate: *"Use lanes: this session is the coordination for <project>."* Skills are invoked as `/lanes:coordination`, `/lanes:writing-briefs`, etc.

## Does it work for front-ends?

Yes, with a few project-level choices in `CLAUDE.md` and the design phase:

- **The contract is an input.** The API spec (generated by the back-end) is the boundary; the front-end mocks it (for example with MSW) and never re-implements business rules — the back-end is the guardian.
- **The design system is the "data model".** Tokens, components and layout rules are decided and built in the core, before screens run in parallel. Screens and flows are the wave briefs.
- **Collision points are different:** shared components, routes and global styles. Put them in the core; give each screen its own folder and route registration line.
- **Acceptance includes what you can see:** component tests, an end-to-end test per flow, and screenshots in the final report. Visual review stays with a human.
- **Different review agents:** a React/accessibility reviewer instead of a database reviewer.

## Requirements

- Claude Code with plugin support. Git worktrees (the lanes work in `.claude/worktrees/`). `gh` for PR checks.
- A project that can set up a fresh worktree with one command and check itself with one command. The `system-design` skill makes sure of both.
